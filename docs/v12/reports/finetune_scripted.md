# 규칙 기반 9종을 대상으로 하는 v12 추가 학습

**후속 변경**: 이 실행은 2026-10-27 사용자 요청으로 3,057,458스텝에서 중단했다. 수동 prior와 강제 작업·회피 선택을 제거한 새 모드는 [learned_control.md](learned_control.md)를 참고하고 `finetune_learned.ps1`로 시작한다. 아래 내용은 변경 전 실행의 기록이다. 수정된 소스로 기존 이름의 실험을 그대로 재개하면 등록 검사에서 거부된다.

2026-10-27 구현. 이 작업에서는 실제 학습과 Unity를 실행하지 않았다. 기존 완료 실험을 수정하는 대신 별도 실행기·출력 경로를 준비했다.

## 실행과 재개

프로젝트 루트의 PowerShell에서 다음 **한 줄**을 실행한다. 첫 실행은 새 학습을 시작하고, 중단 후에는 같은 명령이 마지막 확정 체크포인트에서 재개한다.

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\code\v12\finetune_scripted.ps1
```

Bash: `bash code/v12/finetune_scripted.sh`. 기본 실행은 백그라운드다. 학습 경험 수집 단계에 들어가면 실제 학습 경기 하나가 표시된다. 초기 개발 평가와 중간·최종 평가는 창 없이 수행하므로, **실행 직후에는 창이 뜨지 않을 수 있다.** 학습 창은 평가 동안 닫혔다가 다음 수집 단계에 다시 열린다. 수집 단계 내에서는 게임 프로세스와 창을 재사용한다. 한 wave의 자기 경기가 먼저 끝나면 다른 경기와 GPU 업데이트를 기다리므로 화면이 잠시 멈출 수 있다.

동일 명령 뒤에 다음 옵션을 붙인다.

| 옵션 | 동작 |
|---|---|
| `--status` | 실행 상태·학습 스텝·9종별 최근/최선 승률 확인 |
| `--stop` | 안전한 중단 요청; 확정 체크포인트 보존 |
| `--dry-run` 또는 `--check` | 파일·CUDA·메모리·설정 준비 확인만 수행; Unity·학습 시작 없음 |
| `--resume` | 같은 명령의 자동 재개와 동일 |
| `--name 새이름` | 별도 실험 이름 |

`--stop` 후 `--status`의 `active: false`를 확인하고 재개한다. 정상 중단은 미완료 wave를 학습에 사용하지 않는다. Unity 통신이 막혀 20초의 중단 유예를 넘기면 실행기 소유 프로세스를 종료하고 마지막 확정 업데이트를 보존한다. 완료된 경기 캐시는 재개 시 검증 후 재사용한다. 완료된 실행은 같은 명령으로 다시 학습하지 않는다.

## 학습과 승률 목표

초기 가중치는 `logs/v12/joint_trip_v12/runs/main_F_s11/latest.pt`의 F/seed11 scorer와 critic이다. 새 실험의 Adam 상태는 처음부터 시작한다. 이후 이 실행 자체의 재개는 모델·optimizer·RNG·상대별 누적 배정·단계 상태를 복원한다. 원본 체크포인트와 `artifacts/submission/v12/joint_trip_v12/`는 덮어쓰지 않는다.

대상은 `scripted-noop`, `scripted-random`, `scripted-collector`, `scripted-rush`, `scripted-defender`, `scripted-raider`, `scripted-default`, `scripted-special`, `scripted-weak`의 9종이다. 기존 최종 평가의 runner 기준 승리는 각각 앞의 6종 20/20, default 12/20, special 12/20, weak 11/20이었다. 새 실행은 기존 시험 경기 자체를 학습 데이터로 사용하지 않는다.

- 하나의 F 정책으로 16개 완결 경기를 수집한 뒤 PPO를 업데이트한다. 매 wave에 9종을 모두 포함하고, 나머지 7경기는 개발 평가에서 약한 상대에 더 배정한다. 상대별 양 진영의 경기 수도 균형을 맞춘다.
- 시작 시 개발 평가를 수행하고, 추가 학습 약 524,288 스텝마다 다시 평가한다. 9종 × 4개 맵 × 양 진영 = 회당 72경기다. 같은 개발 맵을 비교·선택에 사용한다.
- 최약 상대의 엄격한 승률을 우선하고 전체 상대 평균을 차순위로 최선 모델을 보존한다. 학습 수집은 확률적 배정, 평가는 실제 배포와 같은 MAP 배정이다.
- 개발 평가에서 **9종 각각 전승**하거나 최대 추가 학습 예산 8,388,608 스텝에 도달하면 모델을 확정한다. 완결 경기 wave 단위로 끊으므로 마지막 wave만큼 예산을 넘을 수 있다.
- 확정한 모델을 독립된 확인 맵에서 9종 × 32개 맵 × 양 진영 = **576경기, 상대별 64경기**로 한 번 평가한다. 확인 결과로 모델을 다시 선택하거나 상대 비중을 조절하지 않는다.
- 개발·확인 평가 모두 9종 각각 전승해야 `empirical_target_met: true`다. 무승부, 패배, 누락·실패·불완전 경기는 전승으로 인정하지 않는다. 미달이면 `target_status: unmet`을 기록하고 종료한다. **이 코드는 유한 표본에서 100%를 목표로 하며, 미지의 모든 경기에서 100%를 보장하지 않는다.**

승패 기준은 기존 실험과 동일한 `provided_runner_v1`, 즉 진영별 누적 runner 보상의 비교다. 유효한 종료 점수 증거도 요구하며, 화면 점수 기준 승리는 `score_wins`에 별도로 기록한다. 두 기준은 기존 180경기 중 7경기에서 달랐으므로 동일하다고 간주하지 않는다.

추가 학습은 새 시드 영역을 쓴다: train 4,100,000–4,999,999, dev 5,100,000–5,199,999, confirmation 5,200,000–5,299,999. 실제 초기 맵 해시의 교차 중복도 검사하며, 원본 실험의 모든 기록된 맵 해시를 새 실행에서 제외한다. 기존 맵 registry를 수정하지 않고 별도 사본의 제외 목록으로 관리한다.

## 자원 배분과 측정 근거

| 항목 | 기본값 |
|---|---|
| 동시 Unity | 16개: 화면 표시 1개 + 백그라운드 15개 |
| CPU | 각 actor/planner 1스레드, BLAS/OpenMP도 1스레드 |
| GPU | CUDA PPO learner 1개, 이벤트 minibatch 128, 최대 4 epochs |
| 학습률 | actor 1e-4, critic 3e-4 |
| PPO | clip 0.2, target KL 0.02, 기존 temperature 1 유지 |
| 게임 속도 | 표시·백그라운드 모두 time_scale 50 |
| 수집 wave | 같은 정책 snapshot의 완결 경기 16개, 업데이트와 수집 분리 |
| 기본 여유 | RAM 4 GiB, 디스크 8 GiB; 시작 시 부족하면 실행 거절 |

이전 [처리량 측정](../../../logs/v12/resource_tuning_20261026_162623/scale_summary.json)에서 8/10/12/14/16/18개의 처리량은 각각 약 404.0/423.2/464.6/455.0/469.0/458.2 env steps/s였다. 20개 진단은 약 463.2였으나 worker 종료 시간 초과가 있어 채택하지 않았다. 따라서 새 측정으로 시간을 쓰지 않고 측정상 최선인 16개를 기본값으로 선택했다. 해당 측정은 Q2 수집 부하였으므로 **표시 창을 포함한 이번 F 추가 학습에서도 전역 최적이라는 뜻은 아니다.**

각 actor는 Unity를 유지하고 정책 업데이트 후 새 가중치를 읽는다. 매 경기마다 정책·상대의 상태와 난수는 다시 초기화한다. 평가 때는 학습 pool을 먼저 닫아 동시에 32개의 게임이 켜지지 않게 한다. 백그라운드 게임도 관측에 필요한 카메라 렌더링은 유지한다. 표시 경기를 1배속으로 낮추면 PPO가 그 경기를 기다리는 병목이 생기므로 기본값은 50배속이다.

기존 정책의 이동 primitive·작업 prior·신경망 구조는 변경하지 않는다. 추가 학습만으로 기존 회피 진동이나 헌터 선택 문제가 반드시 사라진다고 주장하지 않는다. 기존 체크포인트에서는 학습된 보정값이 작았으므로 `updates.jsonl`과 진행 상태에 보정값 크기, 가중치 변화량, KL 등을 기록해 학습이 실제로 진행되는지 확인할 수 있게 했다.

실행 등록은 소스·설정·초기 체크포인트·원본 맵 registry의 해시를 고정한다. 등록 이후 의미가 다른 코드나 설정으로 같은 이름의 실행을 재개하지 않는다. 별도 이름을 쓰면 기존 결과를 보존하면서 새 실행을 만들 수 있다.

검증은 Unity 없는 단위 점검과 실행기 준비 확인으로 제한한다. 실제 게임 처리량·CUDA PPO 업데이트·게임 창 표시는 사용자가 위 명령으로 실행할 때 확인된다.
