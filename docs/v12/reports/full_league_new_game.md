# 새 게임 풀리그 실행 준비 — 2026-11-01

**2026-11-02 최신 게임의 Windows 빌드와 리그 등록을 완료했다.** Unity 6000.3.8f1에서 소스 커밋 `af4c5fa`를 직접 빌드했고, 아래 한 줄 명령으로 새 리그를 시작할 수 있다. 학습·실제 경기는 실행하지 않았다. [설치·자동 빌드 기록](new_game_build.md).

## 등록한 게임 빌드

현재 등록 경로는 `artifacts/builds/windows-af4c5faaf2ef/build-c8231087c08416cc/Blackout.exe`다. API snapshot과 빌드 파일 해시를 별도로 고정했다. 이미 등록을 마쳤으므로 아래 수동 등록 명령을 다시 실행할 필요는 없다.

제공된 `C:\Users\HeXA\Desktop\blackout`은 게임 소스다. 확인한 HEAD는 `af4c5faaf2ef9eae24f536860737099ad56acba3`이며 프로젝트가 지정한 Unity 버전은 **6000.3.8f1**이다. 최초 확인 때 없었던 Editor는 이후 사용자의 빌드 요청에 따라 설치했다. 확인 당시 공식 배포의 v1.1도 이 소스의 빌드가 아니었다.

사용자가 기존 경로를 재확인하도록 요청해, 실제 구 리그의 `manifest.json`에 등록된 `artifacts/builds/windows-v1.1/Blackout.exe`와 빌드 전체를 다시 대조했다. 등록된 201개 파일 중 변경된 것은 실행 중 생성되는 `Blackout_Data/ML-Agents/Timers/Prototype_timers.json` 하나뿐이며, 나머지 200개는 기존 리그 당시와 SHA256이 같았다. 실행 파일·`Assembly-CSharp.dll`·맵 데이터도 그대로다. 게임 저장소의 소스는 업데이트되었지만, 기존 실행 경로의 빌드에는 반영되지 않은 상태다. 이 재확인에서도 게임을 실행하지 않았다.

이 소스로 만든 Windows x86_64 빌드 전체를 등록했다. 실행 파일과 `Blackout_Data/`, `UnityPlayer.dll` 등 빌드 산출물을 함께 보존한다. 원본 저장소를 보존한 작업 복사본에서 빌드했으며, 최초 라이선스 오류는 사용자의 활성화 후 해결됐다.

다음은 최초 수동 등록 방법을 남긴 것이다. 별도 공급 빌드를 등록할 때 `--build`에 전체 빌드 폴더를 넣는다. 이미 등록된 빌드를 덮어쓰지는 않는다.

```powershell
.\.venv\Scripts\python.exe .\code\run.py -m agent_league.new_game_stage --build "C:\경로\새게임빌드" --source-commit af4c5faaf2ef9eae24f536860737099ad56acba3
```

등록은 파일 복사·해시 기록만 수행한다. 공급자가 확인한 소스 커밋을 기록하는 절차이며, 실행 파일 해시만으로 그 소스에서 컴파일되었다고 증명하는 것은 아니다. 기존 빌드·결과를 덮어쓰지 않는다.

## 한 줄 실행

22개 모델의 오프라인 검사를 완료했다. `status.json`은 `checked`, 완료 경기 수는 `0/2310`이며 실제 게임은 아직 시작하지 않았다.

빌드 등록은 완료했다. 프로젝트 루트의 PowerShell에서 실행한다.

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\code\v12\run_league_new_game.ps1
```

동일 명령은 완료된 경기들을 건너뛰고 이어서 실행한다. 실행 중이면 현재 상태만 보여준다. 시작 시 모델 입력 검사를 마친 뒤 게임 창이 나타난다. 경기가 끝나고 다음 경기를 여는 사이에는 창이 잠시 없어질 수 있다. 큐가 소진되는 마지막 구간에는 백그라운드 경기만 남을 수도 있다.

| 항목 | 설정 |
|---|---|
| 참가자 | 기존 고정 21개 + `v12-before-learned`, 총 22개 |
| 선택한 v12 | `artifacts/submission/v12/scripted9_before_learned_latest` |
| 대진 | 231쌍 × 5개 seed × 진영 교대 2경기 = **2,310경기** |
| 모델당 경기 | 상대 21개 × 10경기 = 210경기 |
| 병렬 실행 | 최대 **16개**: slot 0 관전 창 1개 + 백그라운드 15개 |
| 배속 | 관전 1배속, 백그라운드 50배속 요청; 실제 속도는 추론·렌더링에 좌우됨 |
| 추론 | CPU, 각 worker 1스레드 |
| GPU | Unity 의미 지도 렌더링 사용; `-nographics` 비활성화 |
| seed | 기준값 `20261016`; 같은 쌍·반복에서 진영 교대 두 경기에 같은 환경 seed |
| 승패 | 자연 종료 시 `infos.score_0`와 `score_1` 비교, 동점 무승부 |
| 제한 | 22,000스텝, 경기당 실제 시간 7,200초, heartbeat 120초 |
| 실패 | 실행 회차마다 최초 시도 + 재시도 1회; 부분 경기는 결과에서 제외 |
| 여유 자원 | RAM 기본 4 GiB 및 worker 시작 여유, 디스크 기본 15 GiB 및 진행 경기 trace 여유 |
| 출력 | `logs/shared/agent_league/v12_full_league_new_game_20261101/` |

16개는 [기존 자원 측정](../../../logs/v12/resource_tuning_20261026_162623/scale_summary.json)에서 유효한 최고 처리량(약 468.95 env steps/s)을 낸 설정이다. 해당 측정은 이전 게임의 v12 수집 작업이며, **새 게임·22종 혼합·관전 창을 포함한 처리량을 새로 측정한 값은 아니다**. 관전을 위해 한 슬롯을 1배속으로 운영하므로 전체 백그라운드 실행보다 처리량이 낮을 수 있다. 자원 여유가 부족하면 새 경기 투입을 보류한다.

기존 리그의 일부 느린 조합이 1,800초 제한에 걸렸던 점을 반영해 실제 시간 제한을 늘렸다. 자연 종료 규칙이나 정책 행동을 변경하지 않았다. 새 환경에서 실제 1배속/50배속 경기의 맵·행동 일치 검증은 아직 하지 않았다. 각 시도의 slot·배속·창 확인 결과와 초기 맵 해시를 저장한다.

## 상태 확인과 기록

실행 명령 뒤에 다음 옵션을 붙인다.

| 옵션 | 동작 |
|---|---|
| `--list` | 참가자 목록, 게임 실행 없음; 빌드 등록 전에도 가능 |
| `--prepare` | 빌드 등록 후 입력·일정 등록만, 게임 실행 없음 |
| `--check` | 빌드 등록 후 22개 모델의 합성 입력 검사만 |
| `--status` | 실행 여부·완료 수·활성 경기 조회 |
| `--stop` | 새 경기 투입 중단, 진행 경기는 종료 또는 제한 시간까지 기다림 |
| `--resume-check` | 등록 입력과 재개 가능 여부 확인, 실행 없음 |
| `--report` | 저장 결과의 보고서 재생성, 게임 실행 없음 |

실행 폴더의 `report.md`, `ranking.csv`, `summary.json`과 모델·대진·경기별 보고서를 사용한다. 기존 HTML은 구버전 결과이며 새 리그 결과가 자동으로 합쳐지지 않는다.

모든 스텝의 10개 유닛 행동, 96차원 관측 벡터, 보상, 종료 여부와 팀 점수를 저장한다. 의미 지도는 매 스텝 채널 요약과 최초·1,000스텝 간격·종료 시 두 팀 대표 스냅샷을 저장한다. 전체 그래픽 입력을 매 스텝 저장하는 완전 재생 기록은 아니다. 승패는 최종 점수가 기준이고, 누적 보상 승자와 기존 `infos.winner`는 원인 분석용 보조 정보다.
