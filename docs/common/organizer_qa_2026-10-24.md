# 운영진 답변과 v11의 실행 가정

2026-10-24 사용자 제공 질의응답을 정리했다. 별도 공식 웹 공지를 확인했다는 의미는 아니다. 사용자는 답변되지 않은 사항 때문에 계획을 중단하지 말고 [기존 제출 문서](blackout_last_4_pages.md)와 구현을 참고하도록 지시했다.

| 항목 | 제공된 답변 | v11 적용 |
|---|---|---|
| 최종 실행 | ONNX 기반 예정 | 모델을 설계할 때부터 ONNX 추론을 검증한다 |
| 모델 내부 구현 | I/O만 맞추면 자유 | 신경망, tensor로 표현한 계획 연산, 계층적 제어를 사용할 수 있다 |
| `BaseModel`, `MyPolicy`, 생성자, 두 파일 예시 | 필수 내부 구현 규칙이 아님 | 로컬 호환 도구로는 유지 가능하나 v11 설계 제약으로 강제하지 않는다 |
| 스텝 간 내부 상태 | 허용 | 목표, 이전 행동, 정체 이력, recurrent hidden을 활용한다 |
| self-ID·관측 순서·상태 전달 세부 | 구체적인 답변 없음 | 현재 로컬 `act(obs)`의 공개 agent 이름과 canonical batching을 개발 기준으로 사용한다 |
| 대진 횟수·진영 교대 | 답변 없음 | 기존 양 진영 교대 평가를 기본으로 하고 진영별 성적도 보관한다 |

기존 관측 값은 float32 vector 96개와 graphic 96×96×11, 행동은 float32 이동 방향 2개다. 환경의 HWC를 모델 경계에서 CHW로 바꾸는 기존 의미도 유지한다. 원본 게임·API·관측 전처리는 수정하지 않는다.

현재 `blackout_env.model.loader.CheckpointModel.act()`는 공개 이름을 가진 dict를 받은 뒤 이름을 버리고 tensor 두 개만 모델에 넘긴다. v11 개발용 adapter는 그 공개 이름으로 팀의 다섯 행을 정렬하고 행동을 원래 이름으로 되돌린다. 원본 `load_checkpoint`의 코드를 패치할 필요가 없다. 이것은 **현재 로컬 실행에 근거한 개발 가정**이며, 최종 ONNX 실행기가 같은 정보를 전달한다는 운영진 답변은 아니다.

ONNX에서는 Python 객체의 dict/멤버 상태가 자동으로 경기 간 호출에 이어진다고 가정하지 않는다. 개발용 ONNX core는 `state_in → state_out`을 명시하고 adapter가 경기·팀별로 보관한다. 최종 파일의 입력·출력 이름, state 포트, reset 방식은 제출 경계의 manifest와 adapter에서 맞춘다. 이 경계의 조정과 v11의 목표·기억 기반 설계는 별개다. 상세 설계는 [v11 설계](../v11/plans/v11_design.md), 구현 순서는 [v11 구현 계획](../v11/plans/v11_implementation_plan.md)에 있다.

평가 기준에는 기존 자료 사이의 차이가 있다. PPT는 reward가 대회 점수와 무관하다고 설명하지만 로컬 `run_match()`와 이번 리그는 누적 raw reward로 승자를 정한다. 따라서 현재 확인 가능한 로컬 runner 결과를 주 지표로 보존하고, 관측 점수와 향후 제공되는 공식 결과를 별도 필드로 기록한다. 둘을 같은 승률이라고 표기하지 않는다.
